# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

The app is branded **My Thari – Track all my loom production** (logo assets in `public/img/`, generated from the transparent `public/Thari Logo.png` by `scripts/build-logo.py`, which needs Pillow). Internal identifiers such as the backup `format: "loom-saree-backup"`, `localStorage` keys (`loom.*`) and the `LOOM_SUPERVISED` env var keep the old name on purpose, so existing data and sessions keep working.

## Commands

```bash
npm install
npm start          # node launcher.js -> runs server.js on 0.0.0.0:$PORT (default 3000), restarting it on exit code 75; `npm run dev` is identical
npm test           # node --test: the whole suite in tests/ (no extra dependencies, ~4 s)
npm run reset-data # clears every factory's data (keeps factories + users) after a full backup; asks to type RESET
npm run build:win  # dist/MyThari-windows.zip: portable folder with bundled node.exe + .bat launchers
```

CI/CD: `.github/workflows/windows-release.yml` runs on every push to `main` (pushes that only change `*.md` are skipped) and can be started by hand. It runs `npm ci`, `node --check` on every module, `npm test` and `npm run build:win` with `BUILD_NUMBER` = run number, then publishes the GitHub Release `v<package version>-build.<N>` (marked latest) with `MyThari-windows.zip` + `version.json`. It keeps the last 10 build releases. Windows installs upgrade from that release.

Env vars: `PORT`, `DATA_DIR` (default `./data`), `BACKUP_DIR` (default `backups/` next to the data dir), `BACKUP_KEEP_DAYS` (30), `OPEN_BROWSER` (open the browser on start; set by the Windows launcher). A backup folder/retention saved in Settings (`DATA_DIR/settings.json`) overrides the env vars (`backupConfig()` in `paths.js`). `node server.js` works directly, but Settings → Restart needs the launcher (`LOOM_SUPERVISED=1`).

There is no build step or linter. Tests: `npm test` (see **Tests** below). Dependencies: `express`, plus `html2canvas` (pinned 1.4.1), which the server serves from `node_modules` at `/vendor/html2canvas/` so dashboard image export works offline. Verify changes by running the app and using the UI, or the API with a token: `POST /api/auth/login` → `Authorization: Bearer <token>` plus `X-Factory: <factoryId>` on data routes. First login on a fresh data dir is admin/admin. Requires Node >= 18.

## Architecture

### Server modules

- `launcher.js` — forks `server.js`; re-forks when it exits with code 75 (Settings → Restart).
- `server.js` — Express app, factory data API (`/api/data`, `/api/warps`, `/api/bobbins`, `/api/looms`, `/api/deliveries`, `/api/clients`, `/api/stock`, `/api/order`, `/api/staff`, `/api/designs`, `/api/wages`, `/api/expenses`) and domain rules. Every data route sits behind `requireAuth` + `factoryScope`, and handlers use `readDb(req.factoryId)` / `writeDb(req.factoryId, db)`.
- `auth.js` — `/api/auth` (login, me, password) and middleware: `requireAuth`, `requireAdmin`, `factoryScope` (X-Factory header + access check).
- `admin.js` — `/api/admin` router (admin only): factories CRUD, users CRUD, backups (list/download/delete/restore, backup-now, export), backup location, restart.
- `store.js` — `accounts.json` (users + factories), per-factory data files, password hashing, first-start migration.
- `backup.js` — whole-system backup files and log archives. `paths.js` — locations, `settings.json`, `writeJsonAtomic()`.
- `upgrade.js` — version, app status and self-upgrade from GitHub (Settings → App status / Upgrade; `/api/admin/upgrade/check`, `/upgrade`, `/upgrade/token`). The repo and branch come from package.json `repository` / `config.upgradeBranch`. A **git** install (has `.git`) refuses if tracked files have local changes, then fetches, fast-forwards, runs `npm install --omit=dev` if the package files changed, and rolls back with `git reset --hard` if the install or `node --check` fails. A **package** install (Windows, no git or npm) reads `VERSION.json` and checks the latest GitHub Release through its `version.json` asset. To upgrade it downloads `MyThari-windows.zip` (its own zip reader) and uses `MyThari/app/` from it. If there is no release, it falls back to the commit tarball (its own tar reader), refusing if bundled `node_modules` can't satisfy the new dependencies. It copies the files it replaces to `<backup folder>/app-before-upgrade-<stamp>/`, then swaps in the top-level `.js` files, `package*.json`, `public/`, `scripts/` and, from a release, `node_modules/`. `node/` (the running node.exe) and the `.bat` launchers are never replaced. Both take a `db-before-upgrade-…` backup first and restart with exit 75. The repo is private, so package installs need a GitHub token (`settings.githubToken`, read-only Contents). It is sent only to api.github.com, and git uses it as an `http.extraHeader`.

### Data layout (`DATA_DIR`)

- `accounts.json` — `users` `{ id, username, name, role: admin|user, factoryIds, salt, hash, tokenVersion, defaultPassword? }` and `factories` `{ id, name, location, ownerName, ownerPhone, ownerEmail, modules? }`. `modules: { stock, wages, process? }` (Settings → factory → "Use this factory for": **Stock + Wages** or **Stock only**; stock is always on, missing = on; the old Wages-only type was removed and `PUT` rejects `stock: false`; `process: true` is the "Include Process section" checkbox, only for Stock + Wages) turns off the Stock module (`/api/stock`, `/api/clients`; Process + Stock tabs, Home stock panel and report) or the Wages module (`/api/staff`, `/api/designs`, `/api/wages`, `/api/looms/:id/setup`; Designs + Wages tabs, loom design strip, wage on dispatch). The server enforces it with `needModule()` (403) and `modulesOf()`; the page uses `mods()` / `applyModules()`, `[data-mod]` on tabs and `VIEW_MODULE` in `route()`. Warps, looms and dispatch are always on. Data stays when a module is off. Admins can open every factory (their `factoryIds` stay empty); users only their `factoryIds`.
- `factories/<FAC-id>.json` — one factory's `{ warps, bobbins, looms, deliveries, clients, stockMoves, staff, designs, wagePayouts, wageDeductions, deductionRates?, expenses, activity }`. `activity` is the Log page: every data-changing route calls `logEvent(db, req, type, text)` (types `warp|bobbin|loom|dispatch|delivery|process|stock|party|wages|expense`, newest first, with `by`; stock moves get their type from `moveType()`). When adding a route that changes data, log it too. A new log type also needs an option in the Log page's `#logType` filter. Files without `activity` get one built from existing records by `seedActivity()` in `migrateDb()`. `activityVersion` < 2 renames old entries to the dispatch/delivery wording. `store.factoryFile()` only accepts generated `FAC-` ids, so ids can't escape the folder.
- `settings.json` — backup folder/retention and `sessionSecret`.
- First start on an old single-factory install (`initAccounts()`): `db.json` becomes factory "My factory", and the old `settings.admin` login (or admin/admin, flagged `defaultPassword`) becomes the admin user.

All writes are atomic (temp file + rename). Each request reads the factory file, mutates in memory and rewrites it. There is no locking. New records are `unshift`ed, so lists are newest-first. `migrateDb()` (in `readDb`) adds missing collections and backfills `warpId` on old deliveries.

### Auth and permissions

Tokens are stateless `<userId>.<tokenVersion>.<expiry>.<hmac>` (7 days, HMAC with `settings.sessionSecret`), so they survive restarts. Bumping a user's `tokenVersion` signs them out: own password change, or an admin editing another user. The user record is re-read on every request, so role and factory changes apply immediately. Role `user` can do everything in their factories **except** discard warps (`POST /api/warps/:id/discard`) remove looms (`DELETE /api/looms/:id`) and remove staff or designs (`DELETE /api/staff/:id`, `/api/designs/:id`), all `requireAdmin`. Settling wages is open to every user. Settings rules: you can't delete or demote yourself, and at least one admin must remain. Deleting a factory, or resetting it (`POST /api/admin/factories/:id/reset`, which wipes its data but keeps the factory and users), requires `confirmName` and takes a backup first (`before-delete-factory` / `before-reset-factory`).

### Backups (`backup.js`)

Backup files hold the whole system: `{ format: "loom-saree-backup", version: 2, factories, data: { <id>: factoryData } }`. User accounts are not included. `backupNow()` refreshes `db-YYYY-MM-DD.json` on start and hourly and prunes old dailies. `snapshot(label)` writes never-pruned `db-<label>-<day>-<time>.json` (manual, before-reset, before-restore, before-delete-factory). Restoring a v2 file replaces the factory list and data (factories created later disappear from the list) and keeps users, dropping their assignments to missing factories. A v1 file (the old single-factory `{ warps, looms, … }`) gets `needsFactory` and is restored into a chosen factory. Backup names are checked against `BACKUP_NAME` to block path traversal.

Log archives (also `backup.js`): the Log page keeps `LOG_KEEP_DAYS` (30) days. `archiveLogs()` moves older `activity` entries of every factory into `<backup folder>/logs/logs-<day>-<time>.csv` (UTF-8 BOM, opens in Excel; names checked against `LOG_NAME`), then removes them from the factory files. It runs on start and hourly (`safeArchiveLogs()`), and from Settings → Logs (`POST /api/admin/logs/archive`). `GET /api/admin/logs-export` downloads every current log as CSV. Changing the backup folder with "copy existing" also copies `logs/`.

### Frontend (`public/index.html`)

A single page with inline CSS and vanilla JS, no framework. Session state lives in `session` (`token`, `user`, `factories`) and `currentFactoryId`; the token and last factory are kept in `localStorage`. `api()` adds `Authorization` and `X-Factory` headers and shows the sign-in screen on 401. `boot()` → `reloadSession()` (`/api/auth/me`) → `applySession()` (picks the factory, fills the header) → `route()` → `refresh()`. The header has the factory `<select>` (top-left) and the user menu (top-right: Settings for admins, Change password, Sign out). Use `isAdmin()` to hide admin-only controls (✕ discard, 🗑 remove loom, footer full-backup link, Settings).

Hash-routed views (`#home`, `#loomlist` (tab **Looms**), `#warps`, `#bobbins`, `#looms` (labelled **Production**), `#process`, `#stock`, `#designs`, `#staff`, `#wages`, `#log`, `#settings`) are `id="view-<name>"` elements toggled in `route()`; add new views to `views`. Without a factory, only Settings is reachable and `#noFactory` explains why.

- `#home` — dashboard (`renderHome()`): loom and active-warp tables split by width, with colour swatches, plus a Stock panel (every bucket per warp, from `stockOf()`). **Download** / **Share on WhatsApp** build a separate phone-width report (`reportHtml()`, `.mreport`/`.mr-*` CSS: stacked rows, no wide tables), render it off-screen at 480 CSS px with html2canvas and save a 1080 px wide JPG (`dashboardBlob()`). Keep it in step with `#homeReport` when the dashboard changes. WhatsApp uses the Web Share API (HTTPS only) or falls back to `wa.me` + `dashboardText()` and a JPG download.
- `#loomlist` (tab **Looms**) — `renderLoomList()`: read-only tables of every loom, one per width section (Single / Triple, like Production; a section shows only with looms of that width) with Running/Stopped + reason, what it runs on, warp, bobbin, design/staff (Wages module). **⚙ Manage looms** opens `manageLoomsDialog` (`renderManageLooms()`) with Edit / Stop / Resume / Design & staff / Remove per loom. Stop/resume/remove are shared with Production cards (`stopLoom()`, `resumeLoom()`, `removeLoom()`); add/edit use `openLoomDialog()` (`PUT /api/looms/:id`).
- `#warps` / `#bobbins` — kanban boards (Ordered / Ready / Running; completed hidden), split into Single / Triple width sections (`.loomgroup`, built from `STAGES` at startup; a section shows when the factory has looms or active items of that width, else only Single), sharing one implementation: `BOARDS` (per-kind config: collection, API, loom slot, ids), `renderBoard()`, `warpCard(w, K)`, `moveWarp(w, to, K)`, `discardWarp(w, K)`; cards carry `data-item`. Bobbins have one colour (`color`/`colorHex`; `swatchOf()`, `colourText()`). Add forms share `lengthOf(p)` / `updateLength(p)` (p = `warp`|`bobbin`). Pointer-event drag-and-drop works with mouse and touch (touch only from `.grip`); drops only land in the card's own width section. `moveBlock()` mirrors the server move rules.
- `#home` also has the Production panel (`renderProduction()` / `prodStats()`: sarees dispatched per local day (`dayKey()`) for the last 30 days, per loom and all looms; today / 7 / 30 days / all time chips and a per-day table for the last 7 days; removed looms show from their delivery `loomName`).
- `#looms` (tab **Production**) — loom cards (each with today / 7 / 30 day counts) in Single / Triple width sections (a section is hidden when the factory has no looms of that width). Wording: taking sarees off a loom is a **Dispatch** (stored as a `deliveries` record via `/api/deliveries`, `deliveryDialog`; log type `dispatch`), recorded only here. Sending stock to a party is a **Delivery** (bucket `dispatched`, log type `delivery`). Internal names keep the old meaning; only labels changed.
- `#process` — per-warp cards (`renderProcess()`): Dispatched (bucket `sent`) → Delivered/godown → **Send to process** (checking: `sortDialog` from `delivered` into process / mai / damage) → Process → Folding → **Add to stock** (`sortDialog` from `folding`). `SORT_MODE` configures both splits, and other steps use `ask()` / `STOCK_STEP`.
- `#stock` — `renderStock()`: pooled totals only (no warp details) for Stock, Greese (mai, + at cleaning), Lot, Damage and With parties, each with its actions in one shared form `actDialog` configured by `ACTS` (party when needed, then qty), plus the Parties list. The UI says "party" everywhere, but the data keeps `clients` / `clientId` / `/api/clients`.
- `#parties` (tab **Parties**, Stock module) — `renderParties()`: one card per party (holds, priced-delivery value, rates by design) with `+ Add party` / Edit / Remove (`openParty()`, `clientDialog`; Remove is admin-only and refused once the party has deliveries). `client.rates` is `{ designId: ₹ per saree }` (`PUT /api/clients/:id`, `partyRates()` validates; rates only exist when the Wages module has designs). The Stock page's "Delivery to party" form can pick an optional design (`fillActDesigns()`), which `/api/stock/move` prices with that party's rate and saves on the move as `designId/designNo/rate/amount` (refused if the party has no rate for it). Stock-page party list was moved here. **Payments:** each card shows the balance and a `💰 Payments` button (`openPay()`, `payDialog`): sarees billed with rate and amount, priced-return credit, payments received and the balance. `db.partyPayments` `{ clientId, amount, date, mode (Cash|Bank transfer|UPI|Cheque|Other), note, balanceBefore/After, settled }` via `POST /api/clients/:id/payments` (any amount, so an overpayment shows as an advance; "Settle full balance" just prefills the balance) and `DELETE …/payments/:pid`. Balance = Σ amounts of priced `stock>dispatched` moves − Σ amounts of priced `dispatched>stock` returns (a party return can pick a design too, credited at the party's rate) − payments (`partyBalance()` server, `partyLedger()` page). Unpriced deliveries aren't billed. A party with deliveries or payments can't be removed. In the party dialog each design has a tick box and its rate box (enabled when ticked, `renderPartyRates()` / `partyRateState()`); only ticked designs are saved, each needing a rate. `+ New design` adds one from the dialog (ticked, rate focused, other rows kept).
- `#designs` — `renderDesigns()`: design cards (image, wage per saree, looms running it), search, add/edit/remove via `designDialog`.
- `#staff` — `renderStaff()`: staff cards (photo, phone as a `tel:` link, looms, to pay now, last paid), add/edit via `staffDialog` (name, optional phone and photo).
- `#wages` — `renderWages()`: per staff earned / deductions / net pay for the open period, damage deductions (`deductionDialog`), Staff list, past payouts. CSV sheets are built client-side (`wageCsv()`, UTF-8 BOM). Loom cards show a design/staff strip (`loomSetup()`) that opens `setupDialog`, which also opens after a warp is put on a loom.
- `#expenses` — `renderExpenses()`: per-loom costs. Follows the Wages module (`needModule("wages", "Expenses")`, tab `data-mod="wages"`, `VIEW_MODULE`), so Stock-only factories don't have it; data is kept. `db.expenses` `{ loomId, loomName (snapshot, survives loom removal), kind: warp_join|bobbin_join|spares|maintenance, amount, date, qty?, item, vendor, billNo, subtype (maintenance: routine/repair/breakdown/other), warpId/warpName, bobbinId/bobbinName, note }`; `POST/PUT/DELETE /api/expenses` (`expenseBody()` validates; spares need an item; any user may edit or remove). Summary tiles, by-loom table, filterable list; `expenseDialog` shows only the detail fields that fit the chosen type (`syncExpenseKind()`).
- `#log` — `renderLog()`: `db.activity` with a type filter and search, shown 200 at a time.

Tile order: dragging a warp within its column, or a loom within its width section, live-moves the DOM node (`placeAmong()`) and saves the column's ids with `POST /api/order` (sets `order` = index). `byOrder()` sorts by `order`; items without one (new) come first. Dragging a warp to another column still changes its stage (`moveWarp()`).
- `#settings` — `loadSettings()`: factories, users, backups, backup location, restart.

All forms are `<dialog>`s. `ask()` is a generic prompt (select, text/number input, or confirm; resolves `null` on cancel). `toast()` shows confirmations, and `flashIds` highlights cards that just changed. Render every user string through `esc()`. Note: after an `await` in a click handler, `e.currentTarget` is null, so capture it first.

Styling: the first `<style>` block is the original base; the second holds the gradient theme (`:root` tokens, `--grad`) and component styles. The header must not use `overflow:hidden`, or the user menu dropdown gets clipped.

### Domain rules (enforced server-side, mirrored client-side)

- `widthType` is `"single"` or `"triple"`; warps only go on looms of the same width. Looms need only `name` + `widthType`.
- Bobbins (optional, weft) share the warp lifecycle and rules: server `BOARD`, `moveRoute(kind)`, `discardRoute(kind)`, `assignError(loom, item, kind)`. A loom holds one warp (`warpId`) and at most one bobbin (`bobbinId`), same width. A dispatch takes the same meters from both and is refused if the bobbin is short; the delivery records `bobbinId/bobbinName/bobbinRemaining`. `settleSpentWarps()` also completes spent bobbins (they leave the loom; the warp keeps running). Loom cards show the bobbin (`loomBobbin()`, + Bobbin / Take off).
- Low alert: a warp or bobbin on a loom with fewer than `LOW_SAREES` (5) sarees left (`lowSarees()`, `lowItems()`) gets a LOW tag, is listed in the `#lowAlert` banner on every page (`renderLowAlert()`), in the dispatch toast, the Home table, `dashboardText()` and `reportHtml()`. Client-side only.
- Warp lifecycle (stored `status`): `Ordered` → `Ready` (`readyDate`) → `In Use` (`startedAt`) → `Completed`; also `Discarded`. Board moves use `POST /api/warps/:id/move` (`to: ordered|ready|running`, + `loomId`). Allowed moves: ordered↔ready (back to ordered only if never woven), ready/ordered→running, running→ready (frees the loom). `assignError()`/`assignWarp()` are shared by every assignment path except loom creation.
- Delivery: saree length `SAREE_M` = 6.3 m. Meters used = `sarees * 6.3`, divided by 3 on triple width (quantities must be multiples of 3). Optional `lrNumber`.
- A warp with less than 6.3 m left is spent: `settleSpentWarps()` marks it `Completed`, sets the loom to `Warp Completed` and clears the link. The offcut stays in `remainingMeters`. It runs after deliveries and in `readDb()`. New warps must be ≥ 6.3 m. Client mirror: `warpSpent()`.
- Loom state is derived, never stored: `loomState()` (server and page) is Running only when not stopped by hand (`stoppedAt`, `POST /api/looms/:id/stop` / `/resume`), with a warp and, if `needsBobbin`, a bobbin; otherwise Stopped with a reason. When a warp/bobbin is used up the loom records `warpEnded`/`bobbinEnded` (cleared on the next assign) for the reason. Only running looms take dispatches; looms stopped by hand reject assignment. Removing a loom (admin) needs it not running; its warp/bobbin return to Ready. `needsBobbin` is set when adding/editing a loom (can't be turned off with a bobbin on; width can't change with a warp/bobbin on); bobbins only go on looms that need one. Discard is refused while the item is on a loom.
- Stock is derived, never stored: `stockFor(db, warpId?)` / `stockOf(warpId?)` run a ledger over `STOCK_BUCKETS`. With a warp id it covers one warp, without one every warp (the pool). Deliveries fill `sent`. Each `stockMoves` entry takes `qty` from `from` and adds it to `to`, and an adjustment (`type: "adjust"`, no `from`, signed `qty`) changes one bucket. Per-warp moves (`PROCESS_MOVES`, need `warpId`): sent→delivered→process→folding. `POST /api/stock/sort` (`from` + counts, see `SORTS`) splits one warp's sarees: `delivered` into process|mai|damage (checking before process) or `folding` into stock|mai|lot|damage (Add to stock). Both stay tagged with the warp. After that, sarees are pooled: `POOL_MOVES` carry no warp and are checked against pool totals: mai→cleaning→stock (each send is a cleaning batch; a return must name its `batchId` and stay within that batch's pending count, see `cleaningBatches()` on both sides; the Stock page shows a Cleaning register), stock→damage (damage return), stock→dispatched (needs `clientId`), dispatched→stock (party return, limited by `partyHolds()`), damage→returned (to the loom owner = factory owner, stored as `ownerName`). Lot has no outgoing move. `POST /api/stock/adjust` sets the pooled stock/mai/lot/damage count (`ADJUSTABLE`). Moves carry `by` and an optional `note`.
- No Process step for Stock + Wages factories unless `modules.process` is ticked (`noProcess()` / `directStock()`): `stockFor()` / client `stockOf()` fold `sent + delivered + process + folding` into `stock` (derived on read, nothing rewritten; `readDb()` sets a non-enumerable `db.direct`, client `directStock()`), so dispatched sarees are deliverable to parties straight away. The Process tab, `#process` route and the Home stage chips are hidden (`data-direct-hide`). Stock only keeps the Process flow. When a factory stops skipping Process (switched to Stock only, or "Include Process" ticked; `PUT /api/admin/factories/:id`), `flushToStock()` in `admin.js` writes real `auto` stock moves for those buckets so counts don't change.
- Stock migrations in `migrateDb()`: `stockVersion` < 2 gets a `folding` twin for each legacy `stock` move (Folding stage added); < 3 fills `from` on legacy moves and adds one `sent→delivered` move per warp for all earlier deliveries (Sent stage added), so old counts are unchanged.
- Add warp takes the length in meters or sarees (`warpLength()`: sarees × 6.3, ÷ 3 on triple width, multiples of 3 there); only meters are sent to the server. The colour name and picker sync both ways: a known name sets the picker, and picking fills `nearestColourName()` unless the user typed their own name (`dataset.auto`).
- Warp display state comes from `warpState()`, not the stored string. Bars turn red below `LOW_SHARE` (20%). Colours come from `bodyHex`/`borderHex`, or `colourOf()` name mapping.
- Wages: a loom has `designId` + `staffId` (`POST /api/looms/:id/setup`); one staff member can run many looms. A dispatch snapshots `staffId/staffName`, `designId/designNo/designName`, `rate` and `wage` = sarees × rate (every saree counted, also on triple width) via `wageFor()`; it needs both set, otherwise no wage is recorded. Design edits only affect later dispatches. Deliveries with `wage` and no `payoutId` are unpaid. Unpaid wages can be corrected by hand: **✎ Edit** on a staff row (or on a deduction) opens `wageEditDialog` (`openWageEdit()`), which sends only changed rows to `POST /api/wages/edit` `{ staffId, dispatches: [{ id, sarees, rate }], deductions: [{ id, items }] }` (log type `wages`). An edited saree count is stored as `wageSarees` on the delivery (`wageQty()` on both sides; `sarees` stays the dispatched count, so production, warps and stock don't change), and `wage` is recomputed; a deduction left with nothing is removed. Settled records can't be edited. `POST /api/wages/settle` (optional `staffIds`: settle only those staff, the rest keep their open period; payout gets `partial`; UI `settleDialog` / `openSettle()`, also a Settle button per staff row) writes a `wagePayouts` record (period, totals, `lines` from `wageLines()`, mirrored client-side) and stamps `payoutId` on those deliveries: nothing is deleted. Damage deductions (`POST /api/wages/deductions`, `DELETE` while unpaid) are `wageDeductions` records `{ staffId, items: [{ kind: minor|heavy, sarees, rate, amount }], amount }`; the rates used become `db.deductionRates` defaults. `wageLines(deliveries, deductions)` gives each line `amount` (earned), `deducted`, `net`. On settle a negative net is paid as 0 and the rest becomes a `carry: true` deduction (`kind: "carry"`) in the next period; a period holding only carries can't be settled. Payouts store `earned`, `deducted`, `carried`, `total` (paid); older payouts only have `total`. Removing staff or a design (admin only) is refused while a loom uses it. Design images and staff photos are browser-resized JPEG data URLs stored in the record (so backups include them), stripped from `/api/data` by `noImage()` (`hasImage`, `imageAt`) and loaded from `GET /api/designs/:id/image` / `GET /api/staff/:id/image`; the page uses `imgTag(kind, record)` / `loadImages()` / `imgCache` (`IMG_KINDS`). `express.json` limit is 2 MB for this. Settle also takes `adjustments` `{ staffId: { amount, note } }` (other deductions such as an advance) saved as `kind: "other"` deductions in that payout. The wage sheet (`openWageSheet()`, `#sheetView` overlay) is the print-ready Print / Save as PDF view (summary with signature column + one slip per staff); `@media print` prints only it (`body.sheet-open`). It opens after settling and from Wage sheet buttons; CSV (`wageCsv()`) is its Excel button.
- Wage basis: factory setting `wageBasis` `"saree"` (default) or `"shift"` (Settings → factory dialog, `factoryFields()` in `admin.js`), plus `shifts: [{ name, start "HH:MM", hours, rate }]` (1 to 6 shifts, e.g. Day / Night, each with its timing, duration and wage per shift; unique names; shift mode needs at least one and every rate > 0; an older single `shift` reads as "Shift 1" via `shiftsOf()` / `shiftList()`). In the factory dialog Stock only greys out the wage options and paying per saree greys out the shifts (`syncFactoryOptions()`). In shift mode `dispatchWage()` records the weaver and design on a dispatch but no `wage`/`rate`, and pay comes from **shift entries**: `POST /api/wages/shifts { staffId, shiftName (optional with one shift), shifts (0.5 steps), note }` writes `db.wageShifts` `{ staffId, shifts, shiftName, shiftRate (that shift's rate at entry time), wage = shifts × rate, sarees: 0, wageSarees: 0 }` (log type `wages`); `DELETE` while unpaid. `unpaid(db)` / `unpaidWages()` return unpaid dispatches **plus** unpaid shift entries, so totals, settle (`payoutId`), payouts and sheets work unchanged; `wageLines()` (both sides) turns them into items `{ shift: true, designNo: <shift name>, rate, shifts, amount }` and `line.shifts`. Edit-wages only touches dispatches (`unpaidDispatches()`). Wages page shows `+ Shifts` and a Shifts panel in shift mode (`openShifts()`, `shiftDialog`). Switching basis keeps unpaid items of either kind.
- The 6.3 m / triple-width maths and the spent rule exist on both sides (`SAREE_M`; server `isSpent()`, client `warpSpent()`; client delivery maths in `updatePreview()`); change them together.

### Tests (`tests/`, `npm test`)

Node's built-in runner, no dependencies. `tests/helpers.js` starts the real `server.js` on a free port with a throwaway `DATA_DIR`/`BACKUP_DIR` (`startApp({ seed })` can pre-write an old `db.json` or a backup; `newFactory({ modules, … })` makes a factory with specific settings; `runningLoom()` seeds a loom with a warp) and gives a tiny `{ get, post, put, del }` client. Each file starts its own server. Files: `auth` (login, tokens, roles, passwords), `factories` (modules, wage basis/shifts validation, reset/delete, direct-stock vs Process, backups), `production` (warps, bobbins, looms, dispatch maths, stop/resume, edits, log), `stock` (Process flow, sorting, cleaning batches, parties, adjust), `wages` (designs, weavers, multi-design looms, per-saree and shift pay, deductions, settling, corrections), `parties` (rates, priced deliveries/returns, payments and balance), `expenses`, `data` (old db.json migration, v1 backups, log CSV/archive) and `static` (page script parses, every `$("id")` exists, tabs ↔ views ↔ `VIEW_MODULE`, log types, page → API routes, Windows file list, escaping). **When you add a feature, add its tests; when you add a server module, add it to `scripts/build-windows.js` (a test checks this).** The UI itself is not driven by a browser in the suite; use the app for that.

### Windows package

`scripts/build-windows.js` downloads a pinned, checksum-verified Node win-x64 runtime into `.cache/` and copies the app modules (keep its file list in sync when adding server files; it includes `upgrade.js`) and writes `VERSION.json` (git commit + `BUILD_NUMBER`, used by Upgrade; also copied to `dist/version.json` for the release), plus `public/`, `scripts/reset-data.js` and `node_modules` into `dist/MyThari/app/`. The desktop shortcut uses `app/public/img/thari.ico`. It also writes CRLF `.bat` launchers that `call settings.bat`. Data and backups sit next to the launchers, so updating means replacing `app/`.
